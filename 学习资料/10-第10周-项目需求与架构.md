## 1. 项目定位

「手机智能助理」：安卓 App + Python 后端 Agent。用户在 App 语音/文字提需求 → Agent 规划并调用工具 → 结果流式回显 App。

**差异化价值**：你是安卓工程师——别人做纯后端 Agent，你做出「端到端可演示的 App 作品」。求职/转岗时，这个项目展示的是：Agent 工程能力 + 你的主场移动端能力 + 跨端协议设计能力。

## 3. 第二步：架构设计

### 3.1 组件图

```
┌─────────────────────────┐         ┌──────────────────────────────────┐
│ 安卓 App（Kotlin）              │         │ Python 后端（FastAPI）                   │
│  · 对话界面 (RecyclerView)    │  SSE    │  · /api/chat 接口层                    │
│  · Retrofit/OkHttp 对接  │ ──────→ │  · LangGraph Agent（第7~8周成果）        │
│  · 协程 Flow 渲染流式     │         │  · 工具：weather/search API               │
│  · 确认弹窗（危险操作）        │ ←────── │  · 日程 MCP Server（stdio 子进程）        │
└─────────────────────────┘         └──────────────────────────────────┘
```

### 3.2 每个组件的职责边界（自查第一条）

| 组件 | 职责 | 明确不做 |
| --- | --- | --- |
| App | 采集输入、渲染流式、展示确认弹窗 | 不做任何工具逻辑、不存模型 Key |
| FastAPI 接口层 | 会话管理、SSE 推送、异常转协议错误 | 不写 Agent 逻辑 |
| LangGraph Agent | 规划、调工具、多轮循环 | 不关心 HTTP 细节 |
| 工具/MCP | 具体能力执行 | 不做决策 |

判断标准：换掉任何一层，其余层不用改逻辑（App 换 Web 界面、Agent 换框架——都成立就合格）。

### 3.3 数据流图（以天气场景为例）

```
用户输入"苏州今天穿什么"
→ App POST /api/chat {thread_id, message}
→ FastAPI 建 SSE 连接，调 Agent
→ Agent 第1轮: tool_calls=[get_weather(苏州)]
→ FastAPI 推送事件: {"type":"tool_call","name":"get_weather"}   (过程可视化)
→ Agent 第2轮: 拿到温度, 生成穿衣建议文本
→ FastAPI 逐 token 推送: {"type":"delta","text":"建议穿..."}
→ App 渲染气泡，流式追加
→ 事件: {"type":"done"} 关闭流
```

## 4. 第三步：接口定义（本周核心产出）

### 4.1 会话模型

沿用第 8 周概念：App 首次启动生成 `thread_id`（UUID）存本地，后续每次请求携带——服务端 Checkpointer 按 thread 恢复上下文。

### 4.2 对话接口（SSE）

**请求**：`POST /api/chat`

```json
{
  "thread_id": "uuid-xxx",
  "message": "苏州今天穿什么"
}
```

**响应**：`Content-Type: text/event-stream`，逐条事件：

| 事件 type | data 内容 | App 行为 |
| --- | --- | --- |
| `delta` | `{"text": "建议穿"}` | 追加渲染气泡 |
| `tool_call` | `{"name": "get_weather", "args": {...}}` | 显示「正在查询天气…」状态 |
| `interrupt` | `{"question": "确认删除 xx.md？", "id": "..."}` | 弹确认框 |
| `done` | `{"usage": {"total_tokens": 812}}` | 结束加载态 |
| `error` | `{"code": "agent_error", "message": "..."}` | 显示错误提示 |

SSE 消息格式（每个事件两行）：

```
event: message
data: {"type":"delta","text":"建议穿"}

```

**错误路径设计**（自查第三条，逐条写进设计文档）：

| 故障 | 处理 |
| --- | --- |
| LLM API 超时/限流 | 后端重试 1 次 → 仍失败推 `error` 事件，App 提示稍后再试 |
| 工具执行异常 | 已回填给模型自愈（第 6 周护栏）；最终失败推 `error` |
| 中断后 App 被杀 | thread 状态在 checkpoint，App 重开后可恢复会话 |
| App 网络断开 | SSE 断开，后端检测 `client disconnect` 停止生成（省 token） |
| 危险操作 | `interrupt` 事件 → App 弹框 → 用户确认后调确认接口 |

### 4.3 确认接口（配合第 8 周 interrupt）

```
POST /api/chat/resume
{ "thread_id": "uuid-xxx", "approved": true }
```

后端收到后 `Command(resume=...)`，Agent 继续执行，结果仍走 SSE 推回（App 重开 SSE 连接）。

### 4.4 流式方案对比（为什么选 SSE）

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| WebSocket | 双向 | 需要心跳/重连管理，本项目单向推送够用 | 不选 |
| **SSE** | 单向推送正好匹配、基于 HTTP 好调试、自动重连 | 只能服务端→客户端 | **选** |
| 轮询 | 最简单 | 延迟高、体验差 | 不选 |

OkHttp 对 SSE 的支持：`EventSource` 或手动解析流式 body（第 11 周给代码）。对照第 4 周：你在 Python 里手动解析过 `data: {...}` 行，安卓端是同样协议反过来写。
