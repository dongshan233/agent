## 1. Checkpointer：图的存档机制

### 1.1 核心概念

- **Checkpointer**：在每个「超级步」结束后把整个 State 快照保存下来的组件。开发用 `InMemorySaver`（重启即失），生产用 `SqliteSaver`/`PostgresSaver`。
- **thread（线程 id）**：一次会话的标识。同一 thread id 的多次 invoke 共享历史——这就是「会话」。换 thread id 就是开新会话。
- **checkpoint**：某个时刻的完整状态快照，带版本号。图因条件边回走、重试、人工介入恢复时，从 checkpoint 继续。

对照安卓：thread ≈ 会话/用户；checkpointer ≈ `onSaveInstanceState` + 本地持久化的合体；恢复会话 ≈ 进程被杀后从 savedState 重建界面。

### 1.2 用法（三行接入）

```python
from langgraph.checkpoint.sqlite import SqliteSaver   # uv add langgraph-checkpoint-sqlite

with SqliteSaver.from_conn_string("checkpoints.db") as saver:
    app = builder.compile(checkpointer=saver)

    config = {"configurable": {"thread_id": "user-42-session-1"}}   # 会话标识
    r1 = app.invoke({"messages": [("user", "记住我的城市是苏州")]}, config=config)
    r2 = app.invoke({"messages": [("user", "我城市现在多少度？")]}, config=config)
    # 第二次调用时，图自动从 checkpoint 载入上次状态，messages 里已包含第一轮全部历史
```

你没手动拼历史——**框架从 checkpoint 恢复后，把你新输入 merge 进去**。第 4 周「记忆是你拼进 messages 的」依然成立，只是拼历史这个苦役交给了 Checkpointer。

### 1.3 进程重启恢复（本周练习核心）

```python
# 重启进程后，同一 thread_id 继续对话：
config = {"configurable": {"thread_id": "user-42-session-1"}}
reply = app.invoke({"messages": [("user", "我刚才说我的城市是哪？")]}, config=config)
# 模型能答出"苏州" —— 状态来自 checkpoints.db
```

验证手段：`app.get_state(config)` 可随时查看某 thread 当前快照，排障利器。

## 2. 短期记忆 vs 长期记忆

| | 短期记忆 | 长期记忆 |
| --- | --- | --- |
| 载体 | thread 的 checkpoint（messages 等 State） | 跨 thread 的独立存储（store） |
| 生命周期 | 单会话 | 跨会话、跨重启 |
| 内容 | 对话历史 | 用户偏好、事实（「用户是安卓工程师」「偏好苏州」） |
| API | Checkpointer | `InMemoryStore` / 数据库 store |
| 对照安卓 | Activity savedState | SharedPreferences / Room |

长期记忆最小示例：

```python
from langgraph.store.memory import InMemoryStore
store = InMemoryStore()
app = builder.compile(checkpointer=saver, store=store)

# 节点里读写（namespace 相当于"表"，key 相当于"行"）
# 写: store.put(("memory", thread_id), "user_city", {"value": "苏州"})
# 读: item = store.get(("memory", thread_id), "user_city")
```

工程要点：长期记忆的价值在于**进 system prompt**——每个新会话开始时，把用户画像/偏好检索出来拼进 system，模型才真正「记得」。别把记忆当成魔法数据库，它只是「下次启动时给你的一段文本」。

## 3. human-in-the-loop：interrupt 机制

### 3.1 场景

Agent 会调「删除文件」「下单付款」这类不可逆工具。全自动很危险，全自动加白名单又太粗。答案：**关键工具执行前，图暂停，等人确认，人放行才继续**。

### 3.2 机制

在工具节点里调用 `interrupt(payload)`：图立即中断，把 payload 交给调用方，当前 checkpoint 已保存。调用方检查 payload、决定结果，用 `Command(resume=...)` 恢复——图从断点继续，`interrupt()` 的返回值就是 resume 的值。

对照安卓：≈ 弹一个 `AlertDialog`，协程 `suspendCancellableCoroutine` 挂起等回调，用户点确认后 resume——一模一样的挂起-恢复模型。

```python
import json
from langgraph.types import interrupt, Command

def delete_file(state: AgentState) -> dict:
    last = state["messages"][-1]
    results = []
    for tc in last.tool_calls:
        if tc["function"]["name"] == "delete_file":
            args = json.loads(tc["function"]["arguments"])
            # 中断点：暂停整张图，把"待确认操作"抛给调用方
            answer = interrupt({
                "question": f"确认删除 {args['path']} 吗？",
                "tool_call_id": tc["id"],
            })
            if answer.get("approved"):
                outcome = do_delete(args["path"])        # 人放行才真正执行
            else:
                outcome = "用户拒绝删除"
            results.append({"role": "tool", "tool_call_id": tc["id"], "content": outcome})
        else:
            results.append(run_tool_safe(tc))
    return {"messages": results}
```

调用方处理中断：

```python
result = app.invoke({"messages": [("user", "删除 notes/tmp.md")]}, config=config)
state = app.get_state(config)
while state.next:                       # 有待续节点 = 存在未决中断
    payload = state.tasks[0].interrupts[0].value   # 上面的 {"question": ...}
    print("Agent 请求确认:", payload["question"])
    ok = input("y/n> ").strip().lower() == "y"
    result = app.invoke(Command(resume={"approved": ok}), config=config)  # 恢复执行
    state = app.get_state(config)
```

三个要点：

1. **中断是「暂停」不是「取消」**：图的状态已经存档，进程甚至可以退出，明天再 resume 也行（这正是 Checkpointer 的意义）。
2. resume 的值会成为 `interrupt()` 的返回值——节点函数里看起来像一次普通函数调用，实际横跨了任意长的时间和进程重启。
3. `state.next` 非空表示图还停在半路。

### 3.3 生产形态

命令行 demo 里人肉 y/n；生产中 resume 常来自**外部系统回调**：App 弹确认框 → 用户点确认 → 前端调后端 API → 后端 `Command(resume=...)`。这正是第 11 周你的安卓 App 将要做的事——记住这条链路。
