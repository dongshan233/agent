# P1-03 框架对比式学习与文章：第二框架的正确学法

> P1 能力扩展 · 方法论模块（可随时做，不算「三选一」里的场景）。
> 目标：把「学第二个框架」从「又刷完一套教程」变成「产出一份有数据、有判断力的对比文章 + 简历亮点」。

## 学习目标

1. 记住打开「学新框架」闸门的两个条件，其余时候不被新框架带跑
2. 用 1~2 天做**对比式重写**，而不是从头看教程
3. 产出一张基于 trace / eval 数据的对比表，而不是 API 名词对照
4. 写出一篇能被面试官追问的技术文章
5. 把二期成果压成简历 3 行亮点与 10 分钟讲法

---

## 1. 闸门：什么时候才允许学第二个框架

二期 README §2 定的规矩，这里再明确一次。**只有两种情形打开**：

| # | 条件 | 例子 |
| --- | --- | --- |
| ① | 目标岗位 JD 明确写了 | 「熟悉 CrewAI / Microsoft Agent Framework 优先」 |
| ② | 你带着一个 LangGraph 表达得很别扭的**具体问题** | 「我的角色分工用状态图写起来很啰嗦，想看看别人怎么抽象」 |

**其余全部关着**。包括：「大家都学我也学」「这个框架 GitHub star 涨得快」「万一面试问到」。

为什么：2026 年的框架格局已经收敛，每个主流框架都找到了自己的生态位，行业共识是**项目中期换编排层极其痛苦**。你一期第 6 周手写过 150 行循环，第 7 周对照过「框架替我做了什么」——**框架 API 是最容易补的部分，判断力才是难的**。为了 API 再投入两周线性学习，是典型的「囤教程」（一期 README 三条纪律之一）。

### 打开后也别从头看教程

正确姿势：**对比式重写**。选一个你已经有数据的场景，在第二个框架上重写，然后比较。凭手写循环的底子，1~2 天足够。

| 时间 | 做什么 | 产出 |
| --- | --- | --- |
| Day 1 上午 | 读官方 Quickstart（只看当前版本，跳过旧博客） | 能跑通 Hello World |
| Day 1 下午 | 用该框架重写一期场景 #1「苏州今天穿什么」 | 功能等价的实现 |
| Day 2 上午 | 接上 P0-01 trace + P0-02 eval，跑同样 16 条用例 | 两组可比数据 |
| Day 2 下午 | 填对比表、写文章、更新简历 | 文章 + 3 行亮点 |

## 2. 2026 年该看谁（别追冷门）

| 框架 | 心智模型 | 适合 | 主要代价 |
| --- | --- | --- | --- |
| **LangGraph**（你已会） | 有向图 / 状态机，节点 + 条件边 | 需要确定性流程、断点续跑、审计轨迹 | 代码量略多、学习曲线陡 |
| **Microsoft Agent Framework 1.0** | supervisor-as-tool、嵌套 handoff | 企业 Microsoft 栈、复杂组织级协作 | 生态绑定较深；AutoGen 已并入它（旧 AutoGen 教程会过时） |
| **CrewAI** | 角色 / 任务 / 流程（role + task + crew） | 快速搭多 Agent 原型、概念直觉 | 细粒度控制弱；角色抽象层有额外 token 开销 |
| **OpenAI Agents SDK** | 嵌套 handoff、tool-first、MCP 原生 | 已在 OpenAI 栈上的团队 | 与特定供应商接口耦合较紧 |

> **版本警告**（和第 9 周 MCP 规范一样重要）：2026 年 peer GroupChat 架构整体在衰退，AutoGen 已并入 Microsoft Agent Framework 1.0；LangChain 官方推荐 supervisor-as-tool 而非旧 supervisor 库。**搜到 2024~2025 年的「多 Agent 群聊」教程，先看发布日期再决定要不要读。**

**只挑一个**。挑的依据是 JD，不是 star 数。

## 3. 对比式重写的实操清单

### 步骤 1：固定实验对象

用一期场景 #1（天气穿衣建议），因为它最简单、有现成 eval 用例、有 trace 基线。

```powershell
# 先存一组 LangGraph / 手写链路的基线数据
uv run python -m eval.run_eval
Copy-Item eval/last_run.json eval/baseline_langgraph.json
```

### 步骤 2：功能等价实现（示意，按你选框架的当前官方文档调整）

以 CrewAI 风格为例，**这是结构示意，不是可直接粘贴的 API 契约**——官方文档为准：

```python
# experiments/crewai_version.py（示意）
from crewai import Agent, Task, Crew          # 以当前版本官方 Quickstart 为准
from scripts.demo_tools import fake_weather

weather_agent = Agent(
    role="天气助理",
    goal="根据真实天气给出穿衣建议",
    backstory="只依据工具返回的数据，不编造温度",
    tools=[...],                             # 复用一期 get_weather 的 schema
    verbose=False,
)

task = Task(
    description="查询 {city} 当前气温，给出穿衣建议",
    expected_output="含温度数值与穿衣建议的一句话",
    agent=weather_agent,
)

crew = Crew(agents=[weather_agent], tasks=[task])
result = crew.kickoff(inputs={"city": "苏州"})
```

**等价性检查清单**（重写完逐条打勾，否则数据不可比）：

- [ ] 同一个工具实现（同样的 `get_weather` 返回）
- [ ] 同一个模型 + `temperature`
- [ ] 同一个 system 约束（禁止编造、必须先取事实）
- [ ] 同一组 16 条 eval 用例与同一份 `thresholds.yaml`
- [ ] 同样接上 trace，能采集 tokens / 延迟 / 工具调用序列

### 步骤 3：跑同一套门禁采数据

```powershell
# 把 run_eval.py 的 run_task 临时换成第二框架实现，跑全量
uv run python -m eval.run_eval
Copy-Item eval/last_run.json eval/after_other_framework.json
uv run python scripts/compare_runs.py eval/baseline_langgraph.json eval/after_other_framework.json
```

### 步骤 4：填对比表（模板）

`docs/framework-comparison.md`：

| 维度 | LangGraph / 手写链路 | 第二框架 | 我的判断 |
| --- | --- | --- | --- |
| 核心抽象 | State + Node + 条件边 | | |
| 实现一个场景的代码行数 | | | |
| 工具 schema 从哪来 | pydantic `model_json_schema()` | | 一期第 2/5/7/9 周那套能否复用 |
| 循环 / 护栏怎么写 | `recursion_limit` + 手写护栏 | | 死循环谁兜底 |
| 状态持久化 | SqliteSaver / Checkpointer | | 重启后能否续跑 |
| 人工介入 | `interrupt` + `Command(resume=...)` | | 是否等价 |
| 可观测性接入成本 | 一个 hooks（P0-01） | | trace 能不能打通 |
| 单任务平均 token | | | 用 `compare_runs.py` 的真实数字 |
| P95 延迟 | | | |
| 16 条用例完成率 | | | |
| 调试体验 | `app.stream` / trace 树 | | 出问题时能不能定位到步 |
| 适用边界 | 确定性流程、需审计 | | 各自该用在什么场景 |

**不要下的三个结论**：「X 比 Y 好」「X 更简单」「大家都该用 X」。要下的是：「当需求是 A 时我选 X，因为……；当需求是 B 时我选 Y，因为……」——**有条件的判断才叫判断力**。

## 4. 文章结构模板

`docs/articles/agent-framework-comparison.md`（也可发到技术博客）：

```markdown
# 我用同一套 eval 对比了两个 Agent 框架，结论和我想的不一样

## 1. 为什么要做这个对比
一句话背景 + 我原本的假设（别省略，读者要看你被数据打脸的过程）

## 2. 实验设计
同一个工具 / 同一个模型 / 同一组 16 条用例 / 同一个门禁
贴 eval/tasks.json 与 thresholds.yaml 的关键片段
说明怎么保证可比（这是文章可信度的关键）

## 3. 数据
贴对比表（上面那张），至少含 token / 延迟 / 完成率三项真实数字
贴一张 trace 树的截图或文本，展示两者执行结构的差异

## 4. 三个我没想到的事
例：角色抽象层的 token 开销、持久化能力的有无、调试时能不能看到中间步
每条配一段代码或一次排障经历

## 5. 结论：什么时候该用谁
有条件的判断，不是排名

## 6. 附录
复现命令、commit hash、配置版本（config_fingerprint）
```

**写法要点**：

- 用数据，不用形容词。「单任务平均 token 812 → 1096」比「开销略大」有力
- 写清**你原来以为错了的地方**——这是文章最值钱的部分
- 贴复现命令与 commit hash，读者能自己跑
- 别复述官方文档（那是教程，不是文章）

把二期成果压成 3 行，每行都带可验证的数字或产物：

```markdown
- 端到端 Agent 系统（安卓 App + FastAPI + LangGraph + MCP）：3 个场景真机可用，
  16 条自动化评估用例完成率 0.9x，CI 门禁拦截 prompt/配置回归。
- 生产化：全链路 OpenTelemetry 风格 trace、LLM-as-judge 评估流水线、

  工具最小权限 / 幂等 / 注入防护 / 分级自主，Docker + 配置版本化部署。
- 选型判断：用同一套 eval 对比 LangGraph 与 <第二框架>，产出对比文章与
```

### 10 分钟讲法（更新版）

一期第 12 周给的是「架构 → 数据流 → 评估 → 踩坑」。二期升级成六段，每段约 1~2 分钟：

| 段 | 讲什么 | 指给对方看 |
| --- | --- | --- |
| 1 架构 | 组件图 + 分层（MCP 纵向 / A2A 横向，若做了 P2） | `docs/architecture.png` |

| 6 判断力 | 第 6 周手写循环 → 框架替我做了什么 → 选型结论 | 文章 + 对比表 |

## 6. 陷阱清单

| 陷阱 | 后果 | 避免 |
| --- | --- | --- |
| 从头看完整教程 | 两周过去，没有产出 | 只看 Quickstart，直接重写一个场景 |
| 只比 API 名字 | 文章没有信息量 | 用 trace / eval 数据比结构、成本、可靠性 |
| 两边用的模型/工具不一样 | 数据不可比，结论无效 | 步骤 2 的等价性清单逐条打勾 |
| 抄 2024 年群聊式多 Agent 教程 | 学了个已被淘汰的范式 | 查发布日期 + 官方当前文档 |
| 下「X 比 Y 好」的结论 | 一被追问就露怯 | 改成有条件的选型判断 |
| 学完就把第一个框架丢掉 | 项目里两套编排层，维护灾难 | 对比实现放 `experiments/`，**主线不换框架** |
| 简历写「熟悉 X/Y/Z」 | 空洞 | 写「用同一套 eval 对比过，结论是…」 |

**最重要的一条**：对比实现放在 `experiments/` 目录，**不要合并进主线**。二期 README §2 说过，项目中期换编排层极其痛苦。你的产出是判断力和文章，不是把项目重写一遍。
