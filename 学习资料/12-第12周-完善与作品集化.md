# 第 12 周：完善与作品集化

> 阶段五 · 第 12 周（收官周）。目标：仓库达到「可直接作为求职/转岗作品集」的水准，能向别人 10 分钟讲清整个系统。

## 学习目标

1. 补齐另外 2 个场景
2. 建立评估：10 个测试任务，量化完成率/轮次/失败原因
3. 加成本意识：记录每次请求 token 消耗
4. 写出高质量 README（架构图、演示 GIF、评估数据、踩坑记录）
5. 完成 12 周总复盘

## 1. 补齐另外 2 个场景

在第 11 周 MVP 模式上复制推广，每个场景保持最小改动：

- **场景 2（资讯摘要）**：接一个搜索 API 工具 → Agent「搜索 → 挑选 → 摘要」多步链
- **场景 3（日程总结）**：把日程查询做成第 9 周那套 **MCP Server**（这是你架构里预留的 MCP 展示位）

每个场景完成即 git commit。警惕功能膨胀：**只做这 3 个，不为「再加一个」**——3 个做深比 10 个做浅有价值（计划原话，也是大多数项目翻车的原因）。

### 2.2 指标与记录表

| 指标 | 定义 | 采集方式 |
| --- | --- | --- |
| 任务完成率 | 符合 expect 的任务数 / 10 | 人工判定，每任务跑 1 次（可选跑 3 次看稳定性） |
| 平均轮次 | 每任务的模型调用次数 | Agent 日志统计 |
| 失败原因分类 | 死循环 / 早停 / 编造 / 工具报错 / 超范围 | 对照第 5 周四大失败模式归类 |
| P50/P95 延迟 | 首字时间和总时间 | 后端埋点 |

结果记录进 `eval/results.md`，格式示例：

```
| # | 完成 | 轮次 | 失败原因 | 备注 |
| 5 | ✗   | 10   | 死循环   | 城市不存在后反复重试 → 后续修复: prompt加"查不到立即告知" |
```

**发现失败 → 归因 → 修复 → 重跑**，这个闭环哪怕只跑一轮，评估章节就有故事可讲了。哪怕完成率只有 70%，一份诚实的失败分析也比虚高的「全部成功」更有工程价值。

## 3. 成本意识：token 统计

第 4 周你见过响应里的 `usage` 字段，现在把它用起来：

1. 每轮模型调用的 `usage` 累加到该 thread 的计数（内存 dict 或 SQLite）
2. `done` 事件返回真实 `usage`（替换第 11 周的占位函数）
3. 评估跑完后输出汇总：总 token、总成本（按平台单价折算）、每任务平均 token

一行结论的价值：让面试官看到你有**成本意识**——Agent 落地最大的隐性成本就是 token，懂这件事的候选人和不懂的差距一目了然。

顺手做的两个低成本优化（可选）：
- 历史剪枝：超过 N 轮后裁掉最早的对话（第 5 周原则落地）
- 工具返回瘦身：大 JSON 结果回填前截断/摘要

**踩坑记录怎么写**：格式「现象 → 原因 → 修复」。素材来源：你 12 周的 git log 和每周 NOTES/RETRO。典型候选：
- SSE 在 OkHttp 需要 `@Streaming`，否则流式变一次性缓冲
- 模拟器访问宿主机要用 `10.0.2.2`
- 工具描述含糊导致参数错误（第 5 周实验直接引用）
- MCP 旧教程的握手代码在新规范下不适用
- 死循环案例与 recursion_limit 护栏

## 5. 12 周总复盘（对照第 6 周手写版）

写 500 字进 `RETRO.md`，回答三个问题：

**1. 框架解决了什么？**
状态管理（add_messages/checkpointer）、控制流声明化（条件边）、可观测性（stream/trace）、持久化与中断恢复（interrupt）。——每一条你都能指着第 6 周代码说「这里当时手写了，框架用 X 替代」。

**2. 协议解决了什么？**
MCP 把工具从「进程内函数」变成「标准服务」，解耦实现方与消费方；Function Calling schema 一路复用（pydantic → JSON Schema → @tool → @mcp.tool），一套能力贯穿始终。

**3. 哪里依然离不开底层理解？**
调参、schema 设计、失败模式排查、上下文管理——框架不帮你做这些。这就是为什么第 5、6 周坚持手写：框架易学，判断力难学。

## 7. 结业之后

- **保持手感**：给项目加第 4 个场景，或换一个模型供应商跑通（检验接口抽象）
